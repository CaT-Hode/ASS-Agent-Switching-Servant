## RELEASE-v0.4.1（本地）

修复第三方注入模型在 Codex 新版 remote compaction v2 中出现 `expected exactly one compaction output item, got 0 from 2 output items` 的问题。

原因是启用提示词预测时使用原生 OpenAI 入口，Codex 随之采用 v2 压缩协议：在普通 Responses 请求历史末尾加入 `compaction_trigger`，并要求返回一个 `compaction` 项。第三方模型收到未转换的控制项后仍返回普通 reasoning/message，旧 ASS 将 HTTP 200 当作任务成功，直到 Codex 校验压缩项时失败。参考 [Codex v2 压缩实现](https://github.com/openai/codex/blob/ce0323f2f2d3b25e82806cd555237da3db4e1897/codex-rs/core/src/compact_remote_v2.rs) 与 [OpenAI 压缩接口说明](https://developers.openai.com/api/docs/guides/compaction)。

- 仅针对第三方注入模型的 v2 压缩请求，使用同一个供应商和模型生成延续摘要。历史工具调用和结果作为资料参与摘要，不注册或执行工具；不将普通任务回答直接当作压缩摘要。
- 完整摘要生成后，使用 ASS 已有的操作系统加密接口封装一个自包含的 `compaction` 项，并输出完整的 JSON 或 SSE 完成事件。下一次请求由 ASS 解密成历史摘要，支持重复压缩、ASS 重启以及切换到官方模型，不依赖临时文件或进程内缓存。
- 官方原生压缩控制项、加密状态、认证和返回内容继续透传，官方订阅目录和上下文设置保持原有行为。
- 摘要为空、截断、拒绝、包含工具调用、超限、响应流中断或加密不可用时，明确返回失败，不发送成功压缩项。损坏、无法解密或不支持版本的 ASS 压缩状态也不会被静默丢弃。
- 摘要输出上限为 16384 token，保留模型和请求中的较小上限；摘要文本限制 256 KiB，加密封装限制 1 MiB。日志增加 `operation: compaction`，分别记录 HTTP 与任务结果，不记录摘要正文。

先用两个普通输出项、零个压缩项的隔离复现得到失败，再实现修复。相关路由与协议回归 59/59 通过，新增 12 项覆盖三种上游协议、JSON/SSE、失败与重复操作、跨实例读取、官方模型切换和损坏数据保护。

本机安装的 Codex `0.163.0-alpha.10.2` 在隔离 app-server 中使用虚拟凭据、本地模拟上游完成两轮“压缩 → 原会话继续”，均成功；第三方上游没有收到 ASS 加密状态或压缩触发控制项。不读取真实 OAuth，不向引用会话发送消息，不执行其任务。

统一验证：`npm test` 全量 1058/1058 通过（0 失败、0 跳过）；`npm run build` 成功。未扩展无关客户端专项或真实联网测试。

## RELEASE-v0.4.3（本地）

修复 DeepSeek 在 Codex 中完成回答后，完整思考正文仍留在已完成条目的问题。

已读取用户更正后的会话记录。其 DeepSeek 片段的 `summary` 配置为 `none`，但完成记录包含 `reasoning.content[].reasoning_text`，对应的完成事件中 `raw_content` 非空。本机 Codex app-server 0.163.0-alpha.10.2 配合隔离模拟服务已复现：两轮回答完成后，`item/completed` 和 `thread/read` 都保留完整思考文字。没有运行引用会话的任务或更改原会话文件。

DeepSeek 的 [Responses 文档](https://api-docs.deepseek.com/guides/responses_api) 说明，`summary` 参数会被接受但不生成摘要；续聊使用明文 reasoning，不能依赖 `encrypted_content`。Codex 的 [条目转换代码](https://github.com/openai/codex/blob/ce0323f2f2d3b25e82806cd555237da3db4e1897/codex-rs/core/src/event_mapping.rs#L216) 将该正文转换为完成条目的 `raw_content`。因此仅改 `default_reasoning_summary` 或丢掉思考正文，分别无法解决显示残留或会损失续聊状态。

- 仅处理由 ASS 转发到官方 DeepSeek Responses 接口的 Codex 请求。运行中的 reasoning 文本增量保持不变；完成条目不再携带可显示的完整思考正文。
- 原始 reasoning 条目通过已有的 Electron OS 加密能力封装在 `encrypted_content` 中。下一轮请求在 ASS 内还原完整上游条目，不向模型发送 ASS 封装；不增加旁路文件、全局缓存或新的配置。
- JSON、SSE、无工具请求和命名空间／自定义工具请求共用该处理。保留助手最终回答、工具输入输出、用量以及模型思考强度。补齐缺少独立 done 事件的最终 reasoning，重复 done 不生成重复条目。
- 加密不可用、状态损坏或超过固定大小限制时明确失败，不通过删除 reasoning 静默继续。旧的上游加密字段随原条目完整保存。
- 官方订阅模型、其他供应商和已有历史文件保持原样；从 DeepSeek 切回官方时，仍使用原有的外发历史过滤，避免向官方发送第三方思考状态。

## RELEASE-v0.4.4（本地）

修复较慢模型在 ASS 中被误判连接失败或协议不支持的问题。

本轮通过用户已配置的供应商进行少量短请求诊断：当前 Gemini 模型的 Responses 在 55.4 秒后完整完成；使用 ASS 原始 Messages 探测请求并允许更长等待时，在 53.7 秒后返回 HTTP 200、正文和正常结束事件。同一供应商的已配置 Claude 小请求通过 Messages 在 3.2 秒内正常结束。因此 Messages 并非该账户不可用，原来的 20 秒协议检测不足以等待慢模型完成。真实请求使用了已配置凭据，但没有在源码、报告或日志中保存其值；其余回归只用隔离假数据和虚拟时钟。

- 每种协议探测的总时限由 20 秒调整为 90 秒，仍然要求正常结束事件与有效输出才算成功，仍可手动取消。没有对特定供应商或模型 ID 作特殊处理。
- 连接检测的整体预算覆盖三个协议探测和随后的一次模型请求；协议探测完成后，为模型请求单独启动 90 秒时限，避免前面的探测耗尽后续请求的时间。读取模型流正文时也传递取消信号，防止已收到 HTTP 头但正文停滞时无限等待。
- 普通 HTTP 404 可能来自模型或通道路由，不再直接认定协议不支持。405、415 或明确说明不支持该协议／接口的错误仍按已确认不支持处理。
- 旧缓存中仅凭 404 得出的不支持结论，在读取时恢复为未确认；若同一凭据下曾成功，则恢复已有成功证据。此过程不写原缓存、不自动联网，保留原 HTTP 状态和时间。用户主动重新检测后再保存新结果，明确的接口拒绝证据会保留。
- 不修改供应商 Key、Messages 初始接口、思考强度、模型选择、未同步草稿或历史对话。
